# 0001 — 无编排器：人工按 README 执行自包含脚本

- 状态：已接受（2026-09-22）
- 关联：[CONTEXT.md](../../CONTEXT.md)（编排器 / 自包含脚本词条）

## 背景

自动化 VPS 初始化的常见形态是一个总控脚本（`init.sh run [阶段]`）依次调度各阶段脚本。本项目最初的设计也是这样：编排器 + `common.sh` 公共库 + `steps/01-12` 阶段脚本。

需求变化：脚本要从 GitHub 以 raw 单文件方式拉取执行（`bash <(curl -sL .../xx.sh)`），不落仓库、不依赖远端机器上预装 git。

## 决策

**不提供编排器。** 每个脚本完全自包含（公共函数内联，不 source 仓库内文件），通过 raw 拉取单文件独立执行；执行顺序由人按 README 保证；脚本以"前置自检 + 交互闸门"自行防错。

## 被否的替代方案

1. **编排器 + common.sh**：脚本间 source 依赖使单文件 raw 拉取跑不起来，与交付形态直接冲突。
2. **tarball 引导**（curl 拉仓库压缩包解到本地再运行编排器）：多一步解包，且 VPS 上留下需要维护的仓库目录；对"偶尔只跑一个功能"的场景过重。
3. **700 行单文件 init.sh**：raw 拉取体验最纯粹，但阶段审查性差、无法按需只拉取一个脚本，且推翻已定稿的"脚本与步骤号一一对应"映射。

关键推导链：raw 单文件交付 → 脚本必须自包含 → 公共逻辑只能内联 → 内联使编排器失去存在意义。

## 后果

- 公共函数块在各脚本中各有一份拷贝，修改时需同步全部；一致性由 `tools/sync_check.sh` 验证（同名函数 md5 对比，任何修改后必须跑一次并确认输出「一致性 OK」）。2026-09-23 曾因独立演化出现 9 个函数分歧，已统一并以该工具固化检查。
- 步骤顺序错误只能靠"前置自检"防御（如 06-ssh.sh 拒绝在 ufw 未放行新端口时运行），无法从结构上强制。
- 无人值守执行被有意排除：每个脚本强制要求 TTY，拒绝在 cloud-init/user-data 中运行——这是防锁死的设计，不是缺陷。
